# Decisions for issues #3–#19

Decisions taken on 2026-10-23 for the open "To decide" points of the GitHub issues #3–#19, so the implementation
can proceed without waiting. Each decision follows the suggestion in the issue unless a reason is given. Change a
decision deliberately: update this file and the code together.

## #7 Audio

1. MVP sources: one audio station (mixing desk feed), screen audio and video asset audio. Device microphones are
   available but muted by default.
2. The proxy is assumed to be an OBS browser source with "Control audio via OBS"; the runbook says so.
3. One global mixer per production plus "follows the picture" per channel. Levels per scene later.
4. No separate preview mix in studio mode, only PFL per channel.
5. Silence detection: a warning (not an incident) when an audible channel has been silent for more than 10 s.

Pinned details of the implementation (spec 4.10, runbook chapter 20):
- Sources: one audio station per production is the intended use (the API does not limit it), screen sound, video sound and device
  microphones (slot `mic`, code A1, A2 …, one per device; an audio station has nothing else). A device microphone starts muted
  and follows the picture of its device; the station is always audible; screens and videos follow their picture. A video allows
  the modes follow and off only.
- The mixer is global (`Production.AudioChannels`), set with `PUT …/audio/channels` (the listed channels are replaced, others stay,
  all or nothing, `adjusting` while a fader moves). Gain −100 … +10 dB where −100 is silence (shown as −∞; no infinity on the wire),
  sync offset 0 … 500 ms (a delay of the sound), modes always | follow | off. Levels per scene are not built; the channel list
  is the only state, so the export of #14 can take it as a clean list (`audioChannels` of the snapshot).
- Audible = broadcast live ∧ not muted ∧ gain > −100 ∧ mode (always; follow: a visible item of its picture is in the program scene, for a
  microphone any source of its device). The preview is never audible; there is no preview mix, the operator uses PFL.
- Ramps: 20 ms for a cut, a mute or a fader move, 300 ms when the broadcast goes live or ends, the duration of a fade (constant power,
  at most 10 s) for a faded program switch. The same function (`audioRampMs`) is used by the output page and the Regie.
- Output page: Web Audio only, created after the first frame with the other lazy work (the first AudioContext of a browser costs
  about 100 ms on the critical path of the slate, measured in E2E-OUT-01), remote tracks as streams (a muted `<audio>` element keeps them alive), videos through
  `captureStream()`; `?audio=off` for a silent page; the page reports `audio { state, levelDb }`; "Sound on" only while blocked and
  something could be heard. The proxy is assumed to be an OBS browser source with "Control audio via OBS"; an embedding frame needs
  `allow="autoplay"`.
- Regie: fifth dock "Audio" (default weight 1.4, stored layouts get it appended to the bottom zone; the pairing dock takes its place while it is open when both are in the same zone, because five docks leave it too narrow at 1280 px), its own copy of the mix for the
  meters, monitoring off by default and after every reload (Program or PFL of one channel, headphones in Chromium), the key M, its own
  undo history of 60 steps, silence warning after 10 s under −60 dBFS (a warning in the row and the status line, never an incident),
  "Audio blocked" in the output chip.
- Sender: audio station = device kind `audioStation` (pairing form or `?station=audio` on a laptop link); microphones of phones and
  laptops are off until switched on; "Share audio" for screens with the honest note (system sound only in Chrome/Edge on Windows with
  the entire screen, otherwise tab sound, none in Firefox and Safari). Station profile: stereo, echo cancellation, noise suppression and
  automatic gain off, Opus about 128 kbit/s, RED on, DTX off; voice profile: browser processing on, mono.
- Security: the output page and the Regie subscribe to every audio track, so an output link also gives access to the microphones that are
  muted in the mixer. This is accepted for the proxy case (links are secret, per link IP restriction) and is a reason for the Air mode
  to use its own room and tokens (later).
- Duplicate, export and import: the channels of **videos** travel in the manifest (format version 2, `audioChannels`, key `asset:aN`), so a
  copy sounds like the original; the channels of **devices** (station, microphones, screen sound) do not, because devices are never
  copied and a placeholder carries no sound: a new device starts with the defaults of its kind. A file of version 1 imports and its
  videos get the defaults. An imported video is probed again for sound (`hasAudio`, as an upload is), a duplicate keeps the
  value of the original.
- Measurements (E2E on a loaded machine, tones of 440–1100 Hz): mute or fader change heard 6–60 ms after the answer of the request,
  end of the broadcast silent within about 450 ms, the sound of the station reaches the output unchanged in level (±2 dB); the delay
  from the microphone to the output page is 190–640 ms (median 510 ms) with the fake source on a machine at load average 25, recorded by E2E-AUD-16. Lip sync: the sound and the picture of a source travel in separate
  streams and the output page plays the sound through Web Audio, so the browser does not align them for the output; the sync offset
  (0–500 ms) is the tool of the operator; an automatic alignment is not built.

## #8 Format and resolution

1. Formats from a fixed list (16:9, 9:16, 1:1, 4:3) with fixed target resolutions per format.
2. Fixed list, no free values.
3. One format per production.
4. Default for new productions: 16:9 · 1080p.

Implementation notes (2026-10-26): the resolution is named after the short side and the list is 720p and 1080p for every
format (16:9 1280×720 / 1920×1080, 9:16 720×1280 / 1080×1920, 1:1 720×720 / 1080×1080, 4:3 960×720 / 1440×1080). Item
bounds stay absolute (they cover every canvas). A change of format scales and centres the existing elements instead of
re-applying templates, because a scene does not remember its template; it is refused with 409 `broadcast_live` while the
broadcast is live and asks first in the Regie when scenes have elements. The publish resolution of phones does not depend
on the format: the output asks the sources for the size of an element on screen. 4:5 and the 1440p/4K resolutions of the
issue text are not offered (decision 1 fixes the list).

## #12 Performance

1. Measure first with a reproducible harness (fake devices, fixed source counts), then optimise by measurement.
2. Preloading: the preview scene is immediate; other scenes may take about 0.5 s.
3. Scene thumbnails as still images are fine.

Implementation details fixed with the work on #12 (spec 7, 8.3, 8.4, 9.1–9.3, `docs/testing.md` 2.19 and 5.1):

4. **Measuring.** `E2E-PERF-01` (project `perf`, tag `@perf`, not in the smoke set) builds the reference scenario: 4 phones
   (camera 1080p), 2 laptop screens (1440p), 6 scenes, Studio Mode, fake media, three Chromium instances (senders, Regie at
   1280 × 800 and device pixel ratio 1.5, output at 1920 × 1080). CPU time comes from `SystemInfo.getProcessInfo` per browser,
   the main thread from `Performance.getMetrics` and a sampled profile, decoders and encoders from WebRTC `getStats`. The
   container has no GPU, so every codec runs in software: the numbers compare two builds on one machine and are the worst case;
   they never replace the manual measurement on real devices (MAN-16).
5. **Screen codec by capability.** A screen share is VP9 only when `MediaCapabilities.encodingInfo` says the VP9 encoder is
   power efficient (hardware); in every other case, also in a browser that cannot answer, it is H.264. The probe runs once per
   publisher (the share's picker is not delayed by it). Cameras stay H.264. Only a VP9 share has a backup codec (VP8).
6. **Screen frame rate.** A screen sends 15 fps (3 Mbit/s cap, content hint `detail`) unless its slot has the option "Video in
   screen" (sender, per slot, kept per browser): then 30 fps, 4.5 Mbit/s cap, content hint `motion`. Changing the option
   changes a running share without a new picker.
7. **What the output receives.** The program scene and the preview scene, nothing else. The preview scene's sources are
   requested at the size they will have on stage (not the lowest layer any more). A source nobody asks a picture for is
   paused (`setEnabled(false)`: the SFU stops forwarding, the browser stops decoding): on the output after 5 s, in the Regie
   after 10 s, and 1.5 s after its track arrives without a consumer once the page has asked for a picture of anything (a page
   that is still loading registers its consumers later than its tracks arrive, which takes seconds on a busy computer; pausing
   there would cost the first picture a round trip and a keyframe, so the normal time holds until then). A paused element is emptied (`srcObject = null`), so a
   stale picture is never shown when the source returns; the next request resumes it and the picture is back with the next
   keyframe (about 0.5 s). Paused sources do not count as decoded streams.
8. **Scene thumbnails are stills.** One hidden video per source, shared by all thumbnails of a provider, and a snapshot of at
   most 320 × 180 every 1.5 s (`STILL_REFRESH_MS`), shown as an image (JPEG data URL), not as a canvas: a canvas on screen is a layer
   that the browser keeps compositing, and sixteen of them cost the Regie more GPU time in the reference scenario than the
   videos they replaced. The program and preview monitors and the station thumbnails stay live.
9. **Nobody sees it, nobody asks for it.** `watchVisibility` (IntersectionObserver with a 96 px margin, plus
   `visibilitychange`) decides. Monitor and thumbnail renderers and the station thumbnails request nothing while they are not
   visible (hidden dock, collapsed section, scrolled away, background tab); the output renderer never pauses (an OBS browser
   source that is switched off keeps its pictures). A renderer option `pauseWhenHidden` overrides the default.
10. **Requested size.** The size of the picture on screen × the device pixel ratio, at most 1.5, rounded up to 16 px, never
    above the production canvas (#8). The renderers re-read it when the pixel ratio changes.
11. **Frame counting.** `FpsMeter` counts what the videos present (`getVideoPlaybackQuality`, cumulative presented and
    dropped frames) instead of running a permanent `requestAnimationFrame`. `fps` in the output report and the debug overlay
    is therefore the video frame rate of the busiest video, no longer the animation frame rate of the page.
12. **Hold frame.** The rolling copy of a live picture is taken at most once per second at on-screen size. The blur of the held
    state is computed once into the copy (`blurCanvas`); there is no CSS `filter` on the live element. All copies (rolling
    hold frames and stills) share one time budget (`SnapshotBudget`, 4 % of the main thread): converting a 2560 × 1440 frame
    in software takes 50 to 100 ms, and an expensive copy delays the next ones. The first copy of an item and the copy at the
    moment of a loss never wait. (Issue 50.) A copy needs a decoded frame (`readyState` ≥ 2, an edge of at least 16 px: a
    stopped sender sends 2 × 2 black frames) that shows a picture, not transparent and not black, looked at in a scratch
    canvas before it replaces the hold frame; otherwise the previous copy stays. Nothing black on air.
13. **Hardware or software.** Where the browser hides `decoderImplementation`, `encoderImplementation` and `powerEfficient*`
    from a page (Chromium without a live capture), the product asks `MediaCapabilities.decodingInfo` and `encodingInfo` what
    the browser would choose. That says hardware or software, but not which encoder; the name stays unknown.
14. **What the operator sees.** A sender reports `encoder`, `hardwareEncoder` and `qualityLimitation` per slot. The station
    line says "CPU at limit" in amber only for `qualityLimitation = cpu` ("bandwidth" and "other" are not a CPU problem); the
    station details list "Encoding" per slot and "Decoding here" (how this Regie decodes); the monitoring page has the sortable
    column "Encoding" with the same tag. The output page reports `droppedFramesPct`, `decodedStreams` and
    `softwareDecodedStreams`; the output chip says "drops frames" (amber) from 5 % dropped frames of a connected link, and the
    output popover lists "Decoding" and "Dropped frames". Amber means "attention, the picture is still there" (DESIGN.md).
15. **Budget.** `docs/testing.md` 5.1: counts (decoded streams, videos) are exact; loads (CPU, main thread, switching time)
    may exceed their budget by 20 %, `PERF_BUDGET_SCALE` scales them for another machine. The animation frame rate of the Regie
    while dragging is recorded, not budgeted: on a machine that is fully busy and renders in software it swings from 2 to 30.

## #13 Text and lower thirds

1. Three fixed styles plus production colours.
2. Custom fonts later (separate issue); the built-in font first.
3. No timer or countdown here.
4. No global overlays yet; text items live in scenes.

Implementation details fixed with the work on #13 (spec 4.4, 8.3, 9.1):

5. A text is a source of its own (kind `text`, code `T1`, id `txt_…`, stored with the production), shown by scene items
   like a camera, so one lower third can be in several scenes and its content is edited in one place. Show and hide is the
   item's `hidden` flag.
6. A new text item starts **hidden**: the content is prepared before it goes on air, a typo never reaches the output by
   accident. Showing and hiding is an operation, not an edit: it also works on the live scene in Studio Mode and leaves no
   undo step.
7. Deleting a text removes it from every scene (the Regie says how many); there is no `text_in_use` conflict like for media.
8. The colours belong to the production (`textTheme`), not to a text; a contrast below 4.5 : 1 is a warning, never a block.
9. Not built in this step, as the issue marks them optional: hiding a text automatically after N seconds, a list of entries
   with "next" for one lower third, and a keyboard shortcut for show/hide (the digits are scenes and a hidden text has no
   focus target). Follow-ups if the operators ask for them.

## #14 Duplicate and export/import

1. Device items become placeholders.
2. "Duplicate" only; a template is a production named "Template …".
3. Export always includes media.

Pinned details (implementation, spec 4.2.2):

4. **One description.** Duplicate, export and import all go through the manifest (`ProductionExport.Capture` and
   `TransferPlan`): a copy contains exactly what a file carries, and a field that is not in the manifest is not handed on.
   What is not: devices and their secrets, pairings, invites, incidents, output links with their keys and IP restrictions
   (the copy gets a fresh default link), broadcast state, program and preview scene, last transition, log, audit, `isActive`.
5. **Placeholders** are stored per production (`placeholders`, `jsonb`) and appear in the snapshot, not in the output. A
   placeholder is made for every device source a scene uses (as item or as fallback), also when the device is gone; a device
   that no scene uses is not copied at all. Its source reference has a made-up device id, so the items stay valid and say
   "Source missing"; the Regie shows the code and name from the placeholder.
6. **Codes.** A placeholder reserves its code. A device source that no scene uses yet and has the kind of the placeholder takes
   over the code when it is assigned ("Use as K1" makes the new phone K1); a source that is in use keeps its code. This is
   the only way a code of an existing source changes.
7. **Assignment** goes to any camera, screen or medium that exists (any kind, not texts), so a camera placeholder can become
   a picture; one request changes every scene and emits `sceneUpserted` per scene, then `placeholderRemoved`. "Remove" deletes the
   items and fallbacks that name the placeholder. Both are audited (`placeholder.assigned`, `placeholder.removed`).
8. **Never active.** A duplicate and an import are created in standby, the first scene on program, and never become the
   active production; the operator switches in the menu. A running production can be duplicated and exported, because only
   reading happens.
9. **Names.** The copy is "{name} (copy)"; a name that exists gets " (2)", " (3)" (also for an import, the preview shows the
   final name and a warning). There is no limit on the number of productions.
10. **Format.** `formatVersion` starts at 1; the manifest has no ids, parts refer to each other by keys of the file. Older
   versions are migrated in memory (`ManifestMigrator`), newer ones are `unsupported_format`. A part that comes later is a new
   version with a migration that adds an empty part: version 2 is the audio mixer of #7 (`audioChannels`, the channels of videos). The file extension is `.studioflow.zip`, the media
   keep their extension under `media/`, each with its SHA-256.
11. **Limits** (`Transfer:*`, validated at startup): file 4 GiB (Caddy 4100 MiB), 1000 files, 8 GiB unpacked, manifest 8 MiB,
    compression ratio 100 from 1 MiB, plus the domain limits (99 scenes, 32 items, 64 texts, 100 device sources). The ZIP is
    checked twice: by its directory before anything is read, and again while reading (a lying directory is stopped).
12. **All or nothing.** Media are written under the new production id before the transaction and removed on any failure; a crash
    in between can leave an unreferenced folder, documented in the runbook (7.5), not cleaned automatically.
13. **Errors.** New codes `invalid_archive` (400), `unsupported_format` (400), `archive_too_large` (413); media that fail the
    upload checks keep `unsupported_media` (415) and a file with more than the domain allows is `limit_reached` (409). A body
    that crosses the limit while it streams is `archive_too_large` on the import route and stays `unsupported_media` elsewhere.
14. **Audit.** `production.duplicated` (on the copy, with `from`), `production.exported` (on the exported production) and
    `production.imported` (on the new one); a file or a manifest is never recorded in the details.
15. **Regie.** "Duplicate production…", "Export" and "Import…" are in the production menu; the import shows a preview (dry run
    with `?dryRun=true`, the file is uploaded twice) before it creates anything. Assignment is offered in the station row of a
    new device ("Use as K1 · Stage phone") and in "Missing sources" of the Sources dock; no popover, the list opens inline.
16. **Caddy.** One local route for `POST /api/productions/import` (`STUDIOFLOW_MAX_IMPORT`, 15 min response header timeout like
    the asset upload); the export is a plain streamed `GET`.

## #27 Zero-config install

Taken on 2026-10-26, following the recommendations of the issue.

1. Caddy gets its configuration from the API through the Caddy admin API, reachable only on the internal network.
   LiveKit runs in a thin wrapper image that watches `livekit.yaml` in a shared volume and restarts the server process
   on change. No Docker socket anywhere.
2. Default HTTPS port `8443` (tcp and udp), overridable with `STUDIOFLOW_HTTPS_PORT`; nothing listens on port 80.
3. `docker-compose.yml` (build from source) stays for development and is zero-config as well; `.env` is optional in
   both files.
4. The wizard covers account, media address, address and certificate, embedding. The backup schedule and the off-site
   `rclone` target are only in "Server settings", to keep the first run short.

### #27 pinned details

Fixed during the implementation (design: `docs/architecture/implementation-spec.md` section 10, operation: `docs/runbook.md`).

1. **Secrets.** The `init` service makes `postgres-password`, `livekit-api-key` and `livekit-api-secret` once into the volume
   `secrets` (mode 600, owner uid 1654 = the API) and never again; it adopts `POSTGRES_PASSWORD`, `LIVEKIT_API_KEY` and
   `LIVEKIT_API_SECRET` of an old `.env` on the first start. The volume is not part of a backup (a restore on a new server
   works with the new secrets). Nothing prints a secret, no endpoint returns one.
2. **Wizard and settings.** Step 1 is the existing setup of #4 (setup code). Steps 2 to 4 save what the API stores in one row
   of the database; the media step sets `configured`, and until then an admin is led to `/setup/server`. A server that was
   set up with the scripts has an account, so its wizard starts at step 2; the old `.env` values (domain, mode, tokens, node
   IP, embedding) are not imported, the operator enters them (runbook 5.5).
3. **Media address test.** The API lets LiveKit announce the candidate address for 2 minutes; the browser joins two
   throw-away participants through the same origin (`wss://host`) and sends a data message through the media server and
   back. The test names the stage that failed (signalling, transport, data). A change of the saved address restarts LiveKit
   and is refused while a broadcast is live.
4. **Certificates.** `internal` (local CA; a domain is optional, a first visit by IP works through on-demand certificates
   whose `ask` endpoint is internal; `ca.crt` is served; HSTS 3600 s because the browser trusts it by hand), `dns-<provider>`
   for cloudflare, infomaniak, hetzner, desec, route53, gandi and ovh (credentials encrypted in the database, optional
   delegated challenge domain for providers without a module), and `custom` (PEM chain and an unencrypted key, checked for
   parse, match, validity and names). No HTTP-01 and no TLS-ALPN: they need port 80 or 443.
5. **Ports.** Host and container port are the same number (HTTP/3 and LiveKit announce the container-side port).
   `STUDIOFLOW_HTTPS_PORT=443` works because Caddy runs with `net.ipv4.ip_unprivileged_port_start=0`. Every link the API
   builds uses `https://<domain or media address>:<port>` (no suffix for 443).
6. **How Caddy follows the settings.** Caddy starts with a bootstrap Caddyfile that answers 503; the API pushes the real one
   to `/load` of its admin API (a unix socket shared by Caddy and the API only), again after every change and whenever it finds Caddy on the bootstrap again (the maintenance
   loop, every 5 seconds). The loaded server is named `sf-<12 hex of the Caddyfile>`.
7. **LiveKit client URL (issue 44).** The URL in a token is `wss://<Host of the request>`: host and port from the request,
   the scheme from the public base URL (the stack serves HTTPS only; the request scheme is not used, because a call without the
   forwarded protocol would give `ws://`). `LiveKit:PublicUrl` overrides, and outside a request the base URL of the settings is
   used. It is therefore the same name the page was opened with, which is the one its CSP allows.
8. **Backup service.** Automatic backups are off until a schedule is saved (as `COMPOSE_PROFILES=backup` was before). Labels
   `_auto`, `_manual`, `_pre-restore`; only `_auto` is pruned, locally and at the off-site target. "Back up now" is a request
   file in the volume `backup_config`; restore is a command only and refuses while the API holds database connections (the
   operator stops `caddy api livekit`; there is no Docker socket). The service has `CHOWN`, `DAC_OVERRIDE`,
   `DAC_READ_SEARCH` and `FOWNER`: restore must replace files of other users, nothing else mounts the data volumes.
9. **Release.** Four images (`web`, `api`, `livekit`, `backup`); `docker-compose.release.yml` has the tag `latest` and no
   version marker; the bundle has no script. A server pins a version with `STUDIOFLOW_IMAGE_TAG`.
10. **Port in use.** Docker 29 starts a container that failed on a taken port without its network and ports on the next
    `up -d`; the runbook says `docker compose up -d --force-recreate caddy` after freeing the port, or to choose another port.

### #6 pinned details

The details below were fixed for the parallel work on #6 (design: [architecture/i18n-design.md](architecture/i18n-design.md),
working guide: [i18n.md](i18n.md)). D3 and D5 are the two the owner should confirm.

1. **D1 Locales.** `en` (source) and `de-CH`. A browser tag `en` or `en-*` gives `en`; `de` or `de-*` (DE, AT, LI) gives
   `de-CH`; anything else gives `en`.
2. **D2 Setting.** `'auto' | 'en' | 'de-CH'` in `localStorage['studioflow.locale']`, the absent key meaning auto. Regie,
   `/monitoring` and sender share the key (one origin); a `storage` event switches other open tabs live. The output page
   ignores storage: `?lang=`, then `navigator.languages`, then `en`.
3. **D3 Decimal comma.** `Intl.NumberFormat('de-CH')` writes a point ("2.8", "1'234.5"), but the product convention is
   the comma. So `LOCALES['de-CH'].numberTag` is `de-DE` while `dateTag` stays `de-CH`. No thousands separators anywhere
   (the old formatting had none). One field changes if the owner prefers CLDR.
4. **D4 Clock.** Always 24 h (`hourCycle: 'h23'`), also in English (`numberTag 'en'`, `dateTag 'en-GB'`).
5. **D5 "Control room".** The English UI says "Control room" for the Regie; code, docs and file names keep "Regie" as a
   proper noun, glossed once as "Regie (control room)". The word is exempt from the German check.
6. **D6 Quotation marks.** English uses “…” and ’, German « » and ’; both live inside catalogue strings, never in code.
7. **D7 API texts.** English; clients localise by `code`. The UI never shows the server `detail` or field messages, except as
   a last resort for an unknown code. `ApiError.detail` stays for diagnostics.
8. **D8 Server defaults.** English, no contract change: scenes "Welcome", "Presentation", "Break"; slates "Starting soon" and
   "Thanks for watching"; label suffix "· Camera". A documented limitation; a follow-up can add optional seed texts to
   `CreateProductionRequest`.
9. **D9 Scripts.** Ops scripts, `.env.example`, compose messages and CLI output are English and ASCII only (no « », `…` or
   `–`), because Windows PowerShell 5.1 mangles UTF-8 without BOM. They have no i18n layer.
10. **D10 URLs.** `/join/warten` becomes `/join/waiting` and `/o/_uhr` becomes `/o/_clock`: a hard switch without redirect, like
    #3. The PWA manifest gets `lang: "en"` and an English description.
11. **D11 Catalogues** are eager and single: both locales are bundled in every app. Lazy-loading `de-CH` only if the budgets fail.
12. **D12 E2E.** Runs in `en-US` plus a small `de-CH` project (`specs/i18n`). E2E text lives in `tests/e2e/support/text.ts` as
    literal strings and does not import the product catalogue.
13. **D13 Exempt from the German check:** `.impeccable/**`, `docs/history/**`, generated files, the `de-CH` catalogue and the
    German test files (`*.de.spec.ts`).

Results of the foundation spikes:

- **Template typing.** `t('key', params)` is type-checked inside templates under `strictTemplates`: an unknown key, a missing
  parameter, a wrong parameter name and a template-literal key with an impossible member all fail `ng build`. No `| t`
  pipe fallback was needed.
- **`satisfies Namespace<'prefix'>`** rejects keys outside the prefix and non-message values at compile time
  (`packages/i18n/src/types.spec.ts` pins this with `@ts-expect-error`).
- **Reactivity.** A `computed()` and an OnPush template that call `t()` re-render on a language switch without a reload
  (`language-select.component.spec.ts`), as does the document title.
- **Bundles** (production build, raw size, before the work packages add their catalogue files): Regie initial 395 kB
  (warning budget 900 kB, error 1.5 MB), sender initial 319 kB (warning 800 kB, error 1.5 MB). The output bundle stays
  free of Angular (`apps/output/vite.config.ts` aliases only the framework-free `@studioflow/i18n`): 122 kB main chunk
  and 34 kB shared-package chunk.
