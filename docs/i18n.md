# Internationalisation (i18n)

English is the source language of StudioFlow. German (Switzerland, `de-CH`) is the first translation. This page is the
working guide: how a string gets into the product, the rules every change follows, and the checks that enforce them.
The reasoning behind the design is in [architecture/i18n-design.md](architecture/i18n-design.md); the pinned decisions are
in [decisions.md](decisions.md) (section "#6 pinned details").

## What is where

| Piece | Where |
|---|---|
| Typed messages, locale store, number/date helpers | `packages/i18n` (`@studioflow/i18n`, framework-free) |
| Angular glue (signals, `provideI18n`) | `@studioflow/i18n/angular`, imported by `apps/studio` and `apps/sender` only |
| Catalogues | `packages/i18n/src/messages/en/*.ts` and `.../de-CH/*.ts`, one file per area and feature |
| Language setting | `localStorage['studioflow.locale']` = `en` or `de-CH`; absent means automatic (browser language) |
| Checks | `npm run check:i18n`, `npm run check:german` (see "Checks") |

The Regie, `/monitoring` and the sender are one origin and share the setting; another open tab follows a change live.
The output page has no setting: `?lang=de-CH` on its URL wins, then the browser language, then English.

## Adding a string

1. Pick the catalogue file of the feature, for example `regie-scenes.ts`. The file `<area>-<feature>.ts` owns exactly
   the keys `<area>.<feature>.*`. Keys describe the purpose, not the text: `regie.scenes.row.menuLabel`. Keys are flat
   and have at most four segments.
2. Add the English message in `messages/en/regie-scenes.ts`:

   ```ts
   export const regieScenes = {
     'regie.scenes.dock.title': 'Scenes',
     'regie.scenes.count': { '=0': 'No scenes', one: '{count} scene', other: '{count} scenes' },
     'regie.scenes.toast.created': 'Scene “{name}” created',
   } as const satisfies Namespace<'regie.scenes'>;
   ```

   `satisfies Namespace<…>` rejects a key outside the prefix at compile time.
3. Add the German message in `messages/de-CH/regie-scenes.ts`. The file is typed against the English one
   (`Translation<typeof en>`), so a missing key, an extra key or a plain string where English has a plural is a compile
   error. Placeholders and plural categories are checked by `catalogue.spec.ts`.
4. Use it:

   ```ts
   import { t } from '@studioflow/i18n';

   t('regie.scenes.dock.title');
   t('regie.scenes.toast.created', { name });
   t('regie.scenes.count', { count: scenes.length });
   ```

   In a component, declare `protected readonly t = t;` and write `{{ t('regie.scenes.dock.title') }}`,
   `[attr.aria-label]="t('…')"`, `[title]`, `[placeholder]`. The key and the parameters are checked in the template
   under `strictTemplates`; a typo or a missing parameter fails `ng build`. Template literals narrow as well:
   ``t(`media.slot.failure.${failure}`)`` compiles only if every possible `failure` has a key.
5. Do not edit `messages/*/index.ts`. A new file needs `npm run i18n:index` (also run by the integrator); the index files
   are generated, sorted and merged with `merge=union`, so two features never conflict on them.

`common.ts` holds only the words every screen needs (`common.ok`, `cancel`, `close`, `retry`, `save`, `delete`, `back`,
`next`, …) and is frozen: feature files repeat a word rather than extend it.

## The API of `@studioflow/i18n`

```ts
t(key, params?)                      // message in the active locale; key and params are type-checked
tFor(locale)                         // t for a fixed locale: English diagnostics, tests
msg(key, params?) / tm(msg)          // a typed message that is resolved later, when it is shown
key(k)                               // identity, for `satisfies Record<Code, MessageKey>` tables
PlainMessageKey                      // keys that need no parameters (route data, tables)
formatNumber / formatTime / formatDate / formatDateTime / compareText / lowerCase
initLocale / getLocale / getLocaleSetting / setLocaleSetting / onLocaleChange / resetLocaleForTests
LOCALES, SUPPORTED_LOCALES, parseLocaleTag, resolveLocale          // @studioflow/i18n/angular: provideI18n, injectI18n, I18N
```

Resolution order of `t`: active catalogue, then English, then the key itself (reported once with `console.error` and
recorded for tests with `missingKeys()`). A missing parameter leaves `{name}` in place and is reported too.

## Rules

- **R1: no translated string at module scope or in decorator metadata.** A `const TITLE = t('…')` at module level or a
  `host: { 'aria-label': t('…') }` is evaluated once and never follows a language switch. Store a `MessageKey` or a
  `Msg` and resolve it when it is shown (`DOCK_TITLE_KEYS = {…} as const satisfies Record<DockId, MessageKey>`). Routes
  carry `data: { titleKey: 'regie.login.title' satisfies PlainMessageKey }`.
- **Values that outlive an interaction** (banners, slot messages, inline errors, connection labels) hold a key or a
  `Msg`. Toasts (at most 6 s) and one-shot confirmations may hold strings.
- **Code to key** with typed template literals, and tables are `satisfies Record<Code, MessageKey>`.
- **A getter is fine** where an existing API had a constant: `HOLD_OPTIONS[].label` and `LAYOUT_TEMPLATES[].name`
  look up their text when read. Never copy such a value at module scope (the template picker keeps the template, not
  its name).
- **Interpolation:** `{param}` and plural messages. Never assemble a sentence from fragments. `t` never formats a
  number: pass the string from a format helper; `count` is inserted with `String(count)`.
- **Numbers and dates** go through `@studioflow/i18n` or the `format*` functions of scene-model. Outside the package
  these are banned and found by `check:i18n`: `toFixed(…).replace('.', ',')`, `toLocale*String`, `Intl.*` constructors,
  Angular `DatePipe`, `DecimalPipe`, `PercentPipe`, `registerLocaleData`, `LOCALE_ID`. The clock is always 24 h. Numbers
  have no thousands separators.
- **English copy style:** sentence case; no trailing period on labels and buttons; full sentences end with a period;
  British spelling (colour, centre). Quotation marks live inside the catalogue strings: “…” and ’ in English, « » and ’
  in German.
- **`aria-label` and visible text** are separate keys when they differ.
- **Never translated:** the product name, slot codes (K1, S1, M1), LiveKit, OBS, QR, units like Mbit/s, API codes,
  storage keys, the language names ("English", "Deutsch (Schweiz)").
- **The Regie** is "Control room" in the English UI; code, docs and file names keep "Regie" as a proper noun, glossed
  once as "Regie (control room)".
- **API texts** are English; clients localise by `code` and never show the server's `detail` (only as a last resort for
  an unknown code). Server-created defaults (scene names, slates, label suffix) are English.
- **Scripts and ops files** are English and ASCII only; they have no i18n layer.

## Tests

- Unit and component tests run in English: the setup files (`packages/i18n/src/testing-setup.ts` for vitest,
  `apps/*/src/testing/setup-i18n.ts` for `ng test`) call `resetLocaleForTests('en')` before every test.
- A test that asserts German calls `resetLocaleForTests('de-CH')` and lives in a file named `*.de.spec.ts`; the checker
  allowlists those files. To assert a German text in an English spec, take it from the catalogue: `tFor('de-CH')('…')`.
- E2E text lives in `tests/e2e/support/text.ts` as literal strings and does not import the product catalogue.
- A spec that is not converted yet may carry `beforeEach(() => resetLocaleForTests('de-CH'))` with the comment "Not
  converted yet"; remove it with the conversion of that file.

## Checks

| Command | What it checks |
|---|---|
| `npm run i18n:index` | regenerates `messages/*/index.ts` (`--check` verifies them) |
| `npm run check:i18n` | indexes are current; files own only their prefix; keys are unique; banned formatting constructs; module-level `t()`; `@studioflow/i18n/angular` only in the two apps; warnings for unused keys, copies of English in German, keys with more than four segments |
| `npm run check:german` | no German text outside the German catalogue (strings, templates, scripts, docs); `--comments` also flags umlauts in code comments |
| `npm run check` | both of the above and the type check |

`node tools/check-german.mjs [--root <dir>] [--paths <p>…] [--json] [--comments] [--staged]` exits with 0 (clean),
1 (findings) or 2 (usage error, or an allowlist entry that matches no file). What it looks at:

| Rule | Finds |
|---|---|
| H1 | an umlaut or ß (in test files an H1-only line is only noted, because Unicode test data is legitimate) |
| H2 | guillemets « » ‹ › (not in Markdown, not in comments) |
| H3 | German function words: one strong word (`nicht`, `bitte`, `und`, …) or two different weak ones (`der`, `mit`, …) in a line |
| H4 | product vocabulary (`Szene`, `Gerät`, `verbindet`, …), case-sensitive |

Suppress a line with `i18n-ignore: <reason>` on the same or the previous line (`//`, `<!-- -->` or `#` form), or a block
with `i18n-ignore-start` and `i18n-ignore-end`. Exempt files go into `tools/german-allowlist/<package>.json` (one file
per work package): `{ "path": "<glob>", "rules": ["H1"] | "all", "reason": "…" }`. Known violations of `check:i18n` that
a package still has to fix are listed in `tools/i18n-baseline/<package>.json`; an entry that covers nothing is an error,
so the list only shrinks.

The word lists live in `tools/lib/german.mjs` and are calibrated by `tools/lib/german.spec.ts` against 25 German and
25 English UI strings. They are extended beyond the design (`gleich`, `geht`, `kommt` as strong words; a few phrases)
because "Gleich geht's los" would otherwise slip through.

## German style

Swiss spelling: ss instead of ß (Schliessen, gross), « » as quotation marks, an apostrophe ’ for contractions, and a
decimal comma ("2,8 Mbit/s", "0,3 s"; D3). `LOCALES['de-CH']` formats numbers with the rules of `de-DE` (comma,
no grouping) and dates with `de-CH` (24 h, "23.10.2026"). A space before the ellipsis and before the percent sign:
"verbindet …", "78 %". The form of address in instructions is "du" in the sender and an infinitive or "Bitte …" in
the Regie.

## Limitations and follow-ups

- Server-created defaults (scenes "Welcome", "Presentation", "Break"; slates "Starting soon", "Thanks for watching"; the
  label suffix "· Camera") are English whatever the language of the Regie (D8). A follow-up can add optional seed texts
  to `CreateProductionRequest`.
- Both catalogues are bundled in every app (D11). Lazy-loading `de-CH` is a follow-up only if the bundle budgets fail.
- The "Recent events" log uses `LogEntryDto.code` and `params`; `text` is the English fallback for clients that do not
  know a code. Adding a `LogCode` needs a message in `regie-log.ts` (the table is `Record<LogCode, MessageKey>`).
- Spike results of the foundation (template typing, `satisfies Namespace`, OnPush re-rendering, bundle sizes) are in
  [decisions.md](decisions.md), section "#6 pinned details".
